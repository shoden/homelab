# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Homelab: a flat (no roles) Ansible project for self-hosted services. It deploys Nextcloud with its supporting services via Docker Compose; several environments (`prod`, `dev`, ...) can share one host. The `nextcloud` inventory group and the `nextcloud-*` names refer to that stack, not to the project name; prod keeps the original names (`nextcloud-app`, `/opt/nextcloud`, ...). The repo is host/domain agnostic: all site-specific values (host, domain, email, passwords) live in the gitignored `inventory/<env>/` directories (copies of `inventory.example/prod` and `/dev`), never in tracked files. There is no build, lint or test suite.

## Commands

```bash
./run.sh deploy.yml prod      # deploy/update an environment's stack (idempotent). The environment is the 2nd argument (prod, dev, ...); extra args pass through, e.g. -e run_repair=true
./run.sh backup.yml prod       # back up DB, Nextcloud volume (no user files), proxy data and config to backup_dir; prunes to backup_keep
./run.sh restore.yml dev -e backup=latest    # restore a backup (without -e backup it lists them); asks for confirmation
./run.sh reboot.yml      # stop the stack, reboot the host and wait for Nextcloud to be healthy (stack starts at boot via systemd)
./run.sh shutdown.yml    # stop the stack via systemd and power off the host
./run.sh maintenance_on.yml / maintenance_off.yml    # switch Nextcloud maintenance mode on / off (idempotent)
./run.sh release_branch   # pick a branch (fzf), rebase on main, deploy to dev + e2e, ff-merge into main, push main, deploy to prod (release_branch.sh)
./run.sh e2e.yml dev      # run only the Playwright end-to-end test against a deployed environment (deploy.yml runs it as its last step; --skip-tags e2e skips it)
./run.sh deploy.yml dev --check --diff    # dry run
./renovate.sh --local     # dry run of Renovate in Docker: shows which image updates it would propose
ansible-playbook -i inventory/dev playbooks/deploy.yml --syntax-check
./run.sh deploy.yml dev -e clean_install=true   # WIPES that environment's base dir and all its volumes
```

`run.sh` uses `inventory/<environment>` (or `$INVENTORY`) and runs the playbook inside `secretspec run --profile <environment> --` (profile = environment name, or `$SECRETSPEC_PROFILE`/the inventory dir name with `$INVENTORY`), which injects the credentials from `secretspec.toml` as environment variables. With no environment argument it asks (fzf), or takes the only one; it refuses the old single-environment `inventory/hosts.ini` layout. Plain `ansible-playbook` needs `secretspec run --profile <environment> -- ` in front and `-i inventory/<environment>` (`ansible.cfg` has no default inventory on purpose: a directory of environments would load all of them at once).

On the target host, `<stack name>-occ <args>` (prod: `nextcloud-occ`, installed by `deploy.yml`) wraps `docker exec -u www-data <app container> php occ`.

## Architecture

- **Layout**: playbooks live in `playbooks/`, with their `templates/` and `group_vars/all/defaults.yml` next to them (Ansible resolves both relative to the playbook's directory, so they must stay there). `run.sh` accepts `deploy.yml`, `setup` or a path and finds the file in `playbooks/`; with no playbook (or only options as arguments) it opens an fzf picker listing `<file> - <name of the first play>`, read with `yq -r '.[0].name'` (so keep the first play of each playbook named descriptively), and without fzf, yq or a terminal it errors with the list. Run plain `ansible-playbook` from the repo root so `ansible.cfg` and `./inventory` are picked up.
- **Environments** (`stack_env` in each inventory, REQUIRED, no default): each environment (`prod`, `dev`, ...) is its own inventory directory and runs the full stack on **its own host**; two environments must not share a host (ports 80/443/81, same names). `stack_env` is only a label (messages, backup manifest). Names are fixed and identical in every environment, derived from `stack_name: nextcloud` in `playbooks/group_vars/all/defaults.yml`: container names (`container_app`, `container_db`, ...), systemd unit (`stack_service`), occ helper (`occ_helper`), base dir `/opt/nextcloud`, `backup_dir`. **Never hard-code `nextcloud-app`, `nextcloud-stack`, `/opt/nextcloud` etc. in playbooks, tasks or templates: use these variables** (`{{ occ }}` is the ready-made `docker exec ... php occ`). The NPM proxy is deployed in every environment (`with_proxy` defaults to true as an opt-out; the templates wrap it in `{% if %}`). **Prod must keep rendering byte-identical files** (a diff in `.env`, compose, HSTS or the unit restarts prod on the next deploy): after touching a template, render prod before and after (`--check --diff`) and compare. A backup records its `stack_env` and `restore.yml` refuses another environment's backup unless `-e restore_allow_other_env=true`. `reboot.yml`/`shutdown.yml` affect the whole machine.
- **`deploy.yml`** is the main playbook and contains no site values. Project defaults are in `playbooks/group_vars/all/defaults.yml`; the site's values are in `inventory/<env>/group_vars/nextcloud/main.yml`, and **all credentials are in SecretSpec** (`secretspec.toml` declares `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `NEXTCLOUD_ADMIN_USER`, `NEXTCLOUD_ADMIN_PASSWORD`, `NGINX_ADMIN_EMAIL`, `NGINX_ADMIN_PASSWORD`; one profile per environment holds the values). `defaults.yml` maps them to the Ansible variables with `lookup('env', ...)` (an unset secret is empty and the asserts fail). Never put credentials in `inventory/`: `group_vars/nextcloud` beats `group_vars/all`, so they would silently override the SecretSpec values. To add a credential: declare it in `secretspec.toml`, map it in `defaults.yml`, then use it in `env.j2`/the compose template. `inventory.example/` is the committed template. Overrides must go in `group_vars/nextcloud` (the inventory group), because it beats `group_vars/all`; and never define an overridable setting in the play's `vars:`, which would beat inventory vars. A check at the start of the deploy block fails the run if `stack_env`, `nextcloud_domain`, a password (or, where there is a proxy, `nginx_admin_*`) is missing or still a `CHANGE_ME`/`example.com` placeholder.
- **End-to-end test**: `deploy.yml` creates a non-admin Nextcloud test account (`playbooks/tasks/test_account.yml`, `occ user:add --password-from-env`, idempotent; credentials `NEXTCLOUD_TEST_USER`/`NEXTCLOUD_TEST_PASSWORD` from SecretSpec) and ends with `playbooks/tasks/e2e.yml` (tag `e2e`, also `playbooks/e2e.yml`; the deploy runs it only if it changed something that can affect Nextcloud: stack restart, `nextcloud_system_config`, new test account, NPM certificate/proxy host, `run_repair`; `-e e2e_force=true` always runs it), which runs the Playwright project in `e2e/` (Chromium; log in, upload a file, check it over WebDAV, delete it) **on the control machine** (`delegate_to: localhost`) against `https://<nextcloud_domain>`. A failing test fails the run. `-e e2e_headed=true` (and `e2e_slow_mo`) shows the browser (headed Chromium runs with `--disable-gpu`: without it, on a Wayland desktop, the window stayed white and clicks timed out). Playwright's failure snapshot `error-context.md` contains the typed password, so the playbook redacts it after each run and the HTML reporter is off. Playwright traces are off on purpose (they record the typed password). Selectors in `e2e/tests/nextcloud.spec.ts` follow Nextcloud's Files UI and may need adjusting after a major upgrade; `e2e/node_modules`, `test-results` and `playwright-report` are gitignored.
- **Deploy audit**: all of `deploy.yml` (checks and tasks) runs inside one `block`; its last step and its `rescue` include `playbooks/tasks/audit_deploy.yml`, which sends a Telegram message (HTML mode: a headline, `🚀 Homelab deployed` or `❌ Homelab deploy FAILED`, then indented lines `🎯 Environment: <env>`, `🏷️ Version: <short hash linked to the GitHub commit>`, `🧪 Branch: NAME` (only when it is not `deploy_default_branch`), `⌚ Duration: Ns` and, on failure, `💥 Failed task: NAME`) through `playbooks/tasks/telegram_notify.yml` (shared with the e2e failure alert; `TELEGRAM_*` are optional, so no secrets means no message; a failed send only warns). The commit and branch come from `playbooks/tasks/git_state.yml` (read on the control machine at the start of the block), which also backs a guard: environments in `deploy_main_only_envs` (default `prod`) are only deployed from `deploy_default_branch` (`main`; a detached HEAD is refused too, even with `--check`; deploy it to `dev` to try another branch). A workspace with staged or unstaged changes to tracked files (untracked ones are fine) is refused too, so the hash always describes what is deployed; `-e deploy_allow_dirty=true` allows it outside `deploy_main_only_envs` and the message then has a `✏️ With uncommitted changes` line. The rescue then fails the run again, so the exit code is unchanged. The message also lists the commits new on that host: `playbooks/tasks/deploy_commits.yml` reads the host's `deploy_commit_file` (`{{ nextcloud_base_dir }}/deployed-commit`, the full hash of the last successful deploy) before anything changes and runs `git log` on the control machine (max `deploy_audit_max_commits` subjects; also says how many previously deployed commits are gone, e.g. after a rebase or going back to main); the file is written just before the success audit, so a failed deploy (including a failed e2e test) keeps the old value and `--tags` runs without it don't move it. `restore.yml` does not update it. `deploy_telegram_notify: false` turns it off; `--check` never sends. An unreachable host fails before the block and is not reported. New deploy tasks go inside the block.
- **Logs**: `with_log_shipper` (opt-in per environment, on in dev and prod) runs `vector` (journald + Docker container logs, disk buffer) and `docker-proxy` (tecnativa socket proxy, `CONTAINERS=1`, on the internal `logs-network` only: container inspect would leak other containers' env) and ships to VictoriaLogs on the hub at `logs_hub_url` (the hub's LAN IP and port 9428, no NPM host or domain). The hub (`with_monitoring_hub`) runs `victoria-logs` (retention `logs_retention`/`logs_max_disk`, basic auth via `-envflag.enable` + `httpAuth_*` env) and Grafana's `victoriametrics-logs-datasource` (provisioned with `$LOGS_USER`/`$LOGS_PASSWORD`). The hub publishes it on `logs_listen` (default `0.0.0.0:9428`; never forward it on the router) with TLS (`logs_tls`): `tasks/logs_tls.yml` makes a self-signed certificate on the control machine in `certs/` (gitignored; SANs from the hub's `logs_tls_hosts` plus `victoria-logs`), copies it to the hub (`{{ monitoring_dir }}/tls`) and to each shipper (`{{ log_shipper_dir }}/logs-ca.crt`, the only certificate Vector trusts); Grafana's data source (`grafana-victorialogs.yml.j2`) embeds it. Deploy the hub first. The password is SecretSpec `LOGS_INGEST_PASSWORD`, the same value in every profile (required by asserts on the hub and shippers). `vector.yaml` is registered in `stack_config_changed` and holds the logs password (mode 0600, `no_log`): Vector 0.62 does not expand `${VAR}` in the sink's `auth` block, it sends them literally and gets 401; Vector's journal mounts depend on which journal dirs exist on the host (stat in `deploy.yml`). Log alerts (group `logs` in `alerts.yml`) come from metrics, so the one vmalert handles them: the hub's VictoriaMetrics scrapes `victoria-logs` (job `victorialogs`, https + basic auth, `scrape.yml` is therefore mode 0600) and each shipper's Vector metrics on port 9598 (job `vector`, targets derived from `monitoring_targets`, `shipper: false` opts out). With `with_log_shipper` false the compose/.env render byte-identical to before. See `doc/logging.md`.
- **Variable flow is two-stage**: Ansible vars → `playbooks/templates/env.j2` (rendered to `/opt/nextcloud/.env`, mode 0600) → `${VAR}` substitution inside `playbooks/templates/docker-compose.yml.j2`. The compose template uses almost no Jinja itself, so adding a new setting usually means editing `playbooks/group_vars/all/defaults.yml` (or the assert list if required), `playbooks/templates/env.j2`, and `playbooks/templates/docker-compose.yml.j2` together.
- **Stack** (`playbooks/templates/docker-compose.yml.j2`, pinned image versions): `mariadb`, `redis`, `nextcloud` (apache image, waits on DB/Redis healthchecks), `nginx` (Nginx Proxy Manager, the TLS-terminating reverse proxy on 80/443, admin UI on 81, stores its config in the same MariaDB DB). Container names are `nextcloud-*`; playbooks reference them by name (e.g. `nextcloud-app`). The certificate (Let's Encrypt, DNS-01 challenge against OVH, `doc/ovh.md`) and the proxy hosts are created by `deploy.yml` through NPM's REST API: `playbooks/tasks/npm.yml` and `npm_proxy_host.yml` (idempotent get-then-create/update, only for the listed domains; inventory vars `npm_certificate_domains` (comma separated), `proxy_domain`, `nextcloud_domain`; OVH credentials from SecretSpec). They log in with `nginx_admin_*`, which NPM only applies on its first start; the tasks use `no_log` (override with `-e npm_debug=true`) and are skipped in `--check`.
- **Monitoring**: every environment runs `node-exporter` (`with_node_exporter`, host network, port 9100); the hub environment (dev, `with_monitoring_hub: true`) also runs `victoria-metrics` (scrapes `monitoring_targets`, a list of `{name, address}` that must be IPs), `vmalert`, `alertmanager` (Telegram, token from SecretSpec `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`, rendered into a 0600 file owned by uid 65534) and `grafana` (behind NPM at `grafana_domain`, `GRAFANA_ADMIN_PASSWORD`). Config lives in `{{ monitoring_dir }}` on the hub, deployed by `deploy.yml`: templates `scrape.yml.j2`/`alertmanager.yml.j2`, static `playbooks/files/monitoring/` (`alerts.yml`, `pi-hosts.json`; they contain `{{ }}` of other tools, so they are `copy`, never `template`). A change to only those files restarts just victoria-metrics/alertmanager/vmalert (not the stack); a changed compose/.env restarts everything as usual. Grafana's dashboard is provisioned read-only. The three monitoring secrets are `required = false` (only the hub needs them; asserted in `deploy.yml`).
- **Lifecycle / idempotency**: the stack runs as the systemd unit `nextcloud-stack.service` (oneshot, `RemainAfterExit=yes`, `docker-compose up -d` / `down`), so it starts at boot and stops cleanly on shutdown. `deploy.yml` registers the `.env`, compose, HSTS-conf and unit-file tasks and restarts the unit **only if one changed** (`stack_config_changed`); otherwise it just ensures `state: started`. Don't add an unconditional `docker-compose down` before that — the oneshot unit stays "active", so `started` would then not bring containers back. New template files that require a restart must be registered and added to the `stack_config_changed` list. When that flag is set, `docker-compose pull` runs first (task `timeout: 1800`) so new image tags download while the old stack is still up and the unit's 300s `TimeoutStartSec` is not spent on downloads. Image upgrades are driven only by a changed tag in `playbooks/templates/docker-compose.yml.j2` (tags are pinned, nothing is pulled otherwise), so a merged Renovate PR must be `git pull`ed before `./run.sh deploy.yml`.
- **Readiness**: never use `occ status` or the bare container health to decide Nextcloud is up. After an image bump the image entrypoint first rsyncs the new code into the volume and runs `occ upgrade`, and starts Apache only afterwards; `occ status` works on half-copied code meanwhile. `playbooks/tasks/wait_nextcloud.yml` (included by `deploy.yml`, `reboot.yml`, `restore.yml`) polls `status.php` until it answers with `installed` and no `needsDbUpgrade`, and the compose healthcheck is the same `status.php` request (`start_period: 600s`). `occ maintenance:repair` sets maintenance mode on and restores it only if it finishes, so it runs through `playbooks/tasks/repair_nextcloud.yml`, which switches maintenance off again in an `always` step unless it was on before. (A repair run on half-copied code once left the instance in maintenance mode after an upgrade.)
- **Nextcloud settings** are applied read-then-write: `config:system` keys live in the `nextcloud_system_config` var (get, then set only if different). The slow `maintenance:repair --include-expensive` / `db:add-missing-indices` run only after a restart or with `-e run_repair=true`.
- **HSTS** comes from `playbooks/templates/apache-hsts.conf.j2`, bind-mounted read-only into the container's `/etc/apache2/conf-enabled/` (not enabled via `a2enconf`, which would be lost when `docker-compose down` recreates the container).
- **Backups** (`backup.yml`, `restore.yml`, settings `backup_*` / `restore_*` in `playbooks/group_vars/all/defaults.yml`): backups go to `backup_dir` (default `/var/backups/nextcloud`, deliberately outside `nextcloud_base_dir` because `clean_install` deletes that). Each is built in `<ts>.partial` and renamed when verified, so pruning (regex on `^\d{8}T\d{6}Z$`) only ever sees complete ones; `-pre-restore` snapshots don't match it and are never pruned. Nextcloud is in maintenance mode during a backup (turned off in `always`, only if the playbook turned it on). The DB is dumped with `MYSQL_PWD` read from the container's own env, never from the host command line. `restore.yml` wipes the MariaDB data dir and lets the container re-initialise it from the restored `.env` before importing the dump, so the DB users come from `.env`, not the dump. It restores the backup's `docker-compose.yml`/`.env` so image tags match the restored Nextcloud code (Nextcloud cannot be downgraded). `restore.yml` `import_playbook`s `backup.yml` for its safety snapshot.
- **Dependency updates**: Renovate (`renovate.json`, run by `.github/workflows/renovate.yml` or `./renovate.sh`) updates the image tags in `playbooks/templates/docker-compose.yml.j2`. All non-major updates (digest, minor, patch, pin) are automerged once all checks pass, and the container image ones are grouped into one PR (`container images`); majors are offered separately (`separateMultipleMajor`, Nextcloud only upgrades one major at a time) and are merged by hand; the image manager is pointed at the `.j2` file via `managerFilePatterns`. Merging only changes the repo, deploying is still `./run.sh deploy.yml`.
- **Vulnerability scan**: Trivy (Aqua Security), `./trivy.sh [list|images|image REF|fs]` locally in Docker and `.github/workflows/trivy.yml` in CI (PRs touching the compose template or `e2e/package*.json`, pushes to main, weekly, manual). It scans every image pinned in `playbooks/templates/docker-compose.yml.j2` (`./trivy.sh list` reads them with `sed`, so keep `image:` values literal: the script and the CI matrix fail on a templated one) and the repo files (`e2e/package-lock.json`, secrets; `--include-dev-deps` because all of `e2e/` is devDependencies, which Trivy skips by default). Everything is reported (SARIF to the Security tab, one category per image, upload is `continue-on-error` for private repos without GHAS); the job fails only on CRITICAL vulnerabilities **that have a fix** (and CRITICAL secrets). Accepted findings go in `.trivyignore.yaml` (scoped to a path inside the image, with a statement and an `expired_at` date; CI passes it through `TRIVY_IGNOREFILE`, `trivy.sh` with `--ignorefile`). The workflow's actions are pinned to full commit SHAs (comment = release); the Trivy version in `trivy.sh` is `TRIVY_IMAGE`.
- **Architecture diagrams**: C4 model in `doc/architecture/workspace.dsl` (Structurizr DSL, run in Docker by `./architecture.sh serve|check|export`; see `doc/architecture/README.md`). `diagrams/` and `diagrams.md` are generated and committed: never edit them, change the DSL and run `./architecture.sh export` (CI, `.github/workflows/architecture.yml`, fails if they are stale). **When you add or remove a service, a `with_*` flag, an external integration or a playbook step, update `workspace.dsl` in the same change.** Keep the DSL host/domain agnostic (no IPs, domains, credentials). `export` retries on purpose (Colima bind mounts are flaky).
- Uses legacy `docker-compose` (v1 binary from apt `docker-compose` package), not `docker compose`.

## Known quirks

- `REDIS_PASSWORD` in `playbooks/templates/env.j2` reuses `mysql_password`. Passwords land unquoted in `.env`, the compose `redis-server --requirepass` command and the PHP session URL (`?auth=`), so special characters (`< > + = ! $ # ' "`, spaces) truncate or corrupt them (a `<` once cut Redis's password to 10 characters and Nextcloud answered 500 with `WRONGPASS`). A `pre_tasks` assert in `deploy.yml` therefore only accepts `[A-Za-z0-9._-]` (not starting with `-`) for `mysql_password`, the one Redis reuses. The other passwords only travel through `.env`/compose `environment:` into container variables, so they may use most printable characters except space, `$ # ' " `` ` `` and `\`; keep the asserts in sync if you add a password.
- NPM's `INITIAL_ADMIN_EMAIL`/`INITIAL_ADMIN_PASSWORD` only apply on NPM's first start (empty DB); changing them later has no effect.
- `nextcloud_port` is written to `.env` but not used by the compose file.
