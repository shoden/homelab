# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Homelab: a flat (no roles) Ansible project for self-hosted services. It deploys Nextcloud with its supporting services via Docker Compose; several environments (`prod`, `dev`, ...) can share one host. The `nextcloud` inventory group and the `nextcloud-*` names refer to that stack, not to the project name; prod keeps the original names (`nextcloud-app`, `/opt/nextcloud`, ...). The repo is host/domain agnostic: all site-specific values (host, domain, email, passwords) live in the gitignored `inventory/<env>/` directories (copies of `inventory.example/prod` and `/dev`), never in tracked files. There is no build, lint or test suite.

## Commands

```bash
./run.sh deploy.yml prod      # deploy/update an environment's stack (idempotent). The environment is the 2nd argument (prod, dev, ...); extra args pass through, e.g. -e run_repair=true
./run.sh backup.yml prod       # back up DB, Nextcloud volume (no user files), proxy data and config to backup_dir; prunes to backup_keep
./run.sh restore.yml dev -e backup=latest    # restore a backup (without -e backup it lists them); asks for confirmation
./run.sh reboot.yml      # stop the stack, reboot the host and wait for Nextcloud to be healthy (stack starts at boot via systemd)
./run.sh shutdown.yml    # stop the stack via systemd and power off the host
./run.sh maintenance_on.yml / maintenance_off.yml    # switch Nextcloud maintenance mode on / off (idempotent)
./run.sh e2e.yml dev      # run only the Playwright end-to-end test against a deployed environment (deploy.yml runs it as its last step; --skip-tags e2e skips it)
./run.sh deploy.yml dev --check --diff    # dry run
./renovate.sh --local     # dry run of Renovate in Docker: shows which image updates it would propose
ansible-playbook -i inventory/dev playbooks/deploy.yml --syntax-check
./run.sh deploy.yml dev -e clean_install=true   # WIPES that environment's base dir and all its volumes
```

`run.sh` uses `inventory/<environment>` (or `$INVENTORY`) and runs the playbook inside `secretspec run --profile <environment> --` (profile = environment name, or `$SECRETSPEC_PROFILE`/the inventory dir name with `$INVENTORY`), which injects the credentials from `secretspec.toml` as environment variables. With no environment argument it asks (fzf), or takes the only one; it refuses the old single-environment `inventory/hosts.ini` layout. Plain `ansible-playbook` needs `secretspec run --profile <environment> -- ` in front and `-i inventory/<environment>` (`ansible.cfg` has no default inventory on purpose: a directory of environments would load all of them at once).

On the target host, `<stack name>-occ <args>` (prod: `nextcloud-occ`, installed by `deploy.yml`) wraps `docker exec -u www-data <app container> php occ`.

## Architecture

- **Layout**: playbooks live in `playbooks/`, with their `templates/` and `group_vars/all/defaults.yml` next to them (Ansible resolves both relative to the playbook's directory, so they must stay there). `run.sh` accepts `deploy.yml`, `setup` or a path and finds the file in `playbooks/`; with no playbook (or only options as arguments) it opens an fzf picker listing `<file> - <name of the first play>`, read with `yq -r '.[0].name'` (so keep the first play of each playbook named descriptively), and without fzf, yq or a terminal it errors with the list. Run plain `ansible-playbook` from the repo root so `ansible.cfg` and `./inventory` are picked up.
- **Environments** (`stack_env` in each inventory, REQUIRED, no default): each environment (`prod`, `dev`, ...) is its own inventory directory and runs the full stack on **its own host**; two environments must not share a host (ports 80/443/81/19999, same names). `stack_env` is only a label (messages, backup manifest). Names are fixed and identical in every environment, derived from `stack_name: nextcloud` in `playbooks/group_vars/all/defaults.yml`: container names (`container_app`, `container_db`, ...), systemd unit (`stack_service`), occ helper (`occ_helper`), base dir `/opt/nextcloud`, `backup_dir`. **Never hard-code `nextcloud-app`, `nextcloud-stack`, `/opt/nextcloud` etc. in playbooks, tasks or templates: use these variables** (`{{ occ }}` is the ready-made `docker exec ... php occ`). The NPM proxy and Netdata are deployed in every environment (`with_proxy` / `with_netdata` default to true as opt-outs; the templates wrap them in `{% if %}`). **Prod must keep rendering byte-identical files** (a diff in `.env`, compose, HSTS or the unit restarts prod on the next deploy): after touching a template, render prod before and after (`--check --diff`) and compare. A backup records its `stack_env` and `restore.yml` refuses another environment's backup unless `-e restore_allow_other_env=true`. `reboot.yml`/`shutdown.yml` affect the whole machine.
- **`deploy.yml`** is the main playbook and contains no site values. Project defaults are in `playbooks/group_vars/all/defaults.yml`; the site's values are in `inventory/<env>/group_vars/nextcloud/main.yml`, and **all credentials are in SecretSpec** (`secretspec.toml` declares `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `NEXTCLOUD_ADMIN_USER`, `NEXTCLOUD_ADMIN_PASSWORD`, `NGINX_ADMIN_EMAIL`, `NGINX_ADMIN_PASSWORD`; one profile per environment holds the values). `defaults.yml` maps them to the Ansible variables with `lookup('env', ...)` (an unset secret is empty and the asserts fail). Never put credentials in `inventory/`: `group_vars/nextcloud` beats `group_vars/all`, so they would silently override the SecretSpec values. To add a credential: declare it in `secretspec.toml`, map it in `defaults.yml`, then use it in `env.j2`/the compose template. `inventory.example/` is the committed template. Overrides must go in `group_vars/nextcloud` (the inventory group), because it beats `group_vars/all`; and never define an overridable setting in the play's `vars:`, which would beat inventory vars. A `pre_tasks` assert fails the run if `stack_env`, `nextcloud_domain`, a password (or, where there is a proxy, `nginx_admin_*`) is missing or still a `CHANGE_ME`/`example.com` placeholder.
- **End-to-end test**: `deploy.yml` creates a non-admin Nextcloud test account (`playbooks/tasks/test_account.yml`, `occ user:add --password-from-env`, idempotent; credentials `NEXTCLOUD_TEST_USER`/`NEXTCLOUD_TEST_PASSWORD` from SecretSpec) and ends with `playbooks/tasks/e2e.yml` (tag `e2e`, also `playbooks/e2e.yml`), which runs the Playwright project in `e2e/` (Chromium; log in, upload a file, check it over WebDAV, delete it) **on the control machine** (`delegate_to: localhost`) against `https://<nextcloud_domain>`. A failing test fails the run. `-e e2e_headed=true` (and `e2e_slow_mo`) shows the browser (headed Chromium runs with `--disable-gpu`: without it, on a Wayland desktop, the window stayed white and clicks timed out). Playwright's failure snapshot `error-context.md` contains the typed password, so the playbook redacts it after each run and the HTML reporter is off. Playwright traces are off on purpose (they record the typed password). Selectors in `e2e/tests/nextcloud.spec.ts` follow Nextcloud's Files UI and may need adjusting after a major upgrade; `e2e/node_modules`, `test-results` and `playwright-report` are gitignored.
- **Variable flow is two-stage**: Ansible vars → `playbooks/templates/env.j2` (rendered to `/opt/nextcloud/.env`, mode 0600) → `${VAR}` substitution inside `playbooks/templates/docker-compose.yml.j2`. The compose template uses almost no Jinja itself, so adding a new setting usually means editing `playbooks/group_vars/all/defaults.yml` (or the assert list if required), `playbooks/templates/env.j2`, and `playbooks/templates/docker-compose.yml.j2` together.
- **Stack** (`playbooks/templates/docker-compose.yml.j2`, pinned image versions): `mariadb`, `redis`, `nextcloud` (apache image, waits on DB/Redis healthchecks), `nginx` (Nginx Proxy Manager, the TLS-terminating reverse proxy on 80/443, admin UI on 81, stores its config in the same MariaDB DB), and `netdata` (monitoring on 19999). Container names are `nextcloud-*`; playbooks reference them by name (e.g. `nextcloud-app`). The certificate (Let's Encrypt, DNS-01 challenge against OVH, `doc/ovh.md`) and the proxy hosts are created by `deploy.yml` through NPM's REST API: `playbooks/tasks/npm.yml` and `npm_proxy_host.yml` (idempotent get-then-create/update, only for the listed domains; inventory vars `npm_certificate_domains` (comma separated), `proxy_domain`, `netdata_domain`, `nextcloud_domain`; OVH credentials from SecretSpec). They log in with `nginx_admin_*`, which NPM only applies on its first start; the tasks use `no_log` (override with `-e npm_debug=true`) and are skipped in `--check`.
- **Lifecycle / idempotency**: the stack runs as the systemd unit `nextcloud-stack.service` (oneshot, `RemainAfterExit=yes`, `docker-compose up -d` / `down`), so it starts at boot and stops cleanly on shutdown. `deploy.yml` registers the `.env`, compose, HSTS-conf and unit-file tasks and restarts the unit **only if one changed** (`stack_config_changed`); otherwise it just ensures `state: started`. Don't add an unconditional `docker-compose down` before that — the oneshot unit stays "active", so `started` would then not bring containers back. New template files that require a restart must be registered and added to the `stack_config_changed` list. When that flag is set, `docker-compose pull` runs first (task `timeout: 1800`) so new image tags download while the old stack is still up and the unit's 300s `TimeoutStartSec` is not spent on downloads. Image upgrades are driven only by a changed tag in `playbooks/templates/docker-compose.yml.j2` (tags are pinned, nothing is pulled otherwise), so a merged Renovate PR must be `git pull`ed before `./run.sh deploy.yml`.
- **Readiness**: never use `occ status` or the bare container health to decide Nextcloud is up. After an image bump the image entrypoint first rsyncs the new code into the volume and runs `occ upgrade`, and starts Apache only afterwards; `occ status` works on half-copied code meanwhile. `playbooks/tasks/wait_nextcloud.yml` (included by `deploy.yml`, `reboot.yml`, `restore.yml`) polls `status.php` until it answers with `installed` and no `needsDbUpgrade`, and the compose healthcheck is the same `status.php` request (`start_period: 600s`). `occ maintenance:repair` sets maintenance mode on and restores it only if it finishes, so it runs through `playbooks/tasks/repair_nextcloud.yml`, which switches maintenance off again in an `always` step unless it was on before. (A repair run on half-copied code once left the instance in maintenance mode after an upgrade.)
- **Nextcloud settings** are applied read-then-write: `config:system` keys live in the `nextcloud_system_config` var (get, then set only if different). The slow `maintenance:repair --include-expensive` / `db:add-missing-indices` run only after a restart or with `-e run_repair=true`.
- **HSTS** comes from `playbooks/templates/apache-hsts.conf.j2`, bind-mounted read-only into the container's `/etc/apache2/conf-enabled/` (not enabled via `a2enconf`, which would be lost when `docker-compose down` recreates the container).
- **Backups** (`backup.yml`, `restore.yml`, settings `backup_*` / `restore_*` in `playbooks/group_vars/all/defaults.yml`): backups go to `backup_dir` (default `/var/backups/nextcloud`, deliberately outside `nextcloud_base_dir` because `clean_install` deletes that). Each is built in `<ts>.partial` and renamed when verified, so pruning (regex on `^\d{8}T\d{6}Z$`) only ever sees complete ones; `-pre-restore` snapshots don't match it and are never pruned. Nextcloud is in maintenance mode during a backup (turned off in `always`, only if the playbook turned it on). The DB is dumped with `MYSQL_PWD` read from the container's own env, never from the host command line. `restore.yml` wipes the MariaDB data dir and lets the container re-initialise it from the restored `.env` before importing the dump, so the DB users come from `.env`, not the dump. It restores the backup's `docker-compose.yml`/`.env` so image tags match the restored Nextcloud code (Nextcloud cannot be downgraded). `restore.yml` `import_playbook`s `backup.yml` for its safety snapshot.
- **Dependency updates**: Renovate (`renovate.json`, run by `.github/workflows/renovate.yml` or `./renovate.sh`) updates the image tags in `playbooks/templates/docker-compose.yml.j2`. Majors need approval in the Dependency Dashboard issue and nothing is automerged; the image manager is pointed at the `.j2` file via `managerFilePatterns`. Merging only changes the repo, deploying is still `./run.sh deploy.yml`.
- Uses legacy `docker-compose` (v1 binary from apt `docker-compose` package), not `docker compose`.

## Known quirks

- `REDIS_PASSWORD` in `playbooks/templates/env.j2` reuses `mysql_password`. Passwords land unquoted in `.env`, the compose `redis-server --requirepass` command and the PHP session URL (`?auth=`), so special characters (`< > + = ! $ # ' "`, spaces) truncate or corrupt them (a `<` once cut Redis's password to 10 characters and Nextcloud answered 500 with `WRONGPASS`). A `pre_tasks` assert in `deploy.yml` therefore only accepts `[A-Za-z0-9._-]` (not starting with `-`) for `mysql_password`, the one Redis reuses. The other passwords only travel through `.env`/compose `environment:` into container variables, so they may use most printable characters except space, `$ # ' " `` ` `` and `\`; keep the asserts in sync if you add a password.
- NPM's `INITIAL_ADMIN_EMAIL`/`INITIAL_ADMIN_PASSWORD` only apply on NPM's first start (empty DB); changing them later has no effect.
- `nextcloud_port` is written to `.env` but not used by the compose file.
